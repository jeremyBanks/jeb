# GZ001: git-zoom with Branching Capability

## GZ001.scheme

This document uses a structured requirement/verification annotation scheme for traceability.

### Identifiers

Every section and item has a hierarchical identifier: `{PROJECT}.{section}.{subsection}.{item}`

- Sections use headers: `## GZ001.goals`
- Items within sections end with: `r[GZ001.goals.item-name]`

### Annotation Types

| Marker | Meaning | Usage |
|--------|---------|-------|
| `r[ID]` | **Requirement** | Defines a requirement, goal, feature, or constraint |
| `s[ID]` | **Satisfies** | This item contributes to satisfying requirement ID |
| `v[ID]` | **Verifies** | This item tests/validates requirement ID |
| `d[ID]` | **Depends on** | This item depends on ID being correct (for subtle/non-obvious dependencies) |

### Rules

1. An `r[]` defines something that must be true or exist
2. An `s[]` or `v[]` appears alongside code/items that implement or test an `r[]`
3. Multiple `s[]` may satisfy one `r[]`; one item may satisfy multiple `r[]`
4. `s[]` and `v[]` may appear on other `r[]` definitions (sub-requirements)
5. `d[]` marks non-obvious algorithmic or action-at-distance dependencies
6. Use `rg` / grep to navigate: find an `s[X]` → search for `r[X]` to understand why

### Example

```markdown
## PROJ.goals

Users can encode arbitrary bytes to printable text.
r[PROJ.goals.encode-bytes]

## PROJ.features

The `encode()` function accepts `&[u8]` and returns `String`.
r[PROJ.features.encode-fn] s[PROJ.goals.encode-bytes]

## PROJ.tests

Roundtrip: `decode(encode(x)) == x` for all `x`.
r[PROJ.tests.roundtrip] v[PROJ.features.encode-fn]
```

## GZ001.constraints

Every commit reachable from a git head before an operation must remain reachable after. No history rewriting.
r[GZ001.constraints.no-history-edit]

## GZ001.goals

Transform between full-repository and subdirectory views while preserving git semantics, enabling multi-repo integration within a monorepo workflow.
r[GZ001.goals.transform-views]

Branch names encode zoom state, enabling independent remotes per zoomed path.
r[GZ001.goals.branch-naming]

Support vendoring external repositories into subdirectories without bloating the child repo with full monorepo history (shallow mode). Shallow mode may upgrade to full mode, but not downgrade (downgrade would require history editing).
r[GZ001.goals.vendor-without-history] d[GZ001.constraints.no-history-edit]

No duplicate commits for in-tree vs out-of-tree representations, unlike `git subtree`.
r[GZ001.goals.no-duplicate-commits]

Standard git tools (merge, show, diff, log) should produce correct/expected results without special flags when there's an obviously-right behavior.
r[GZ001.goals.git-tools-just-work]

Each view sees its own representation as first-parent history. Changes made in other views appear as merges into this view.
r[GZ001.goals.first-parent-identity]

All zoom metadata is stored in git trailers or implied by the graph structure itself. No external state.
r[GZ001.goals.metadata-in-git]

First-parent chains are the primary lens for understanding history. Many git commands default to first-parent traversal; we lean into this.
r[GZ001.goals.first-parent-focus]

## Discussion

### Branch Naming Convention

Settled on: `{branch},path={path}`

Examples:
- `trunk,path=src/bin`
- `main,path=crates/jeb`

Properties:
- Shell-safe (no expansion in bash/zsh)
- Parseable: split on `,path=`
- Git-legal refname
- Extensible: could add `,remote=...` later

### Core Operations (Sketched)

```bash
# Zoom into a subdirectory
git checkout trunk
git zoom src/bin
# Now on: trunk,path=src/bin

# Zoom out (merge back)
git zoom out
# Back on trunk, changes merged

# Fetch external repo into current path
cd src/bin
git zoom fetch https://github.com/jeremyBanks/bin
# Sets up trunk,path=src/bin with remote pointing to external repo
```

### Vendoring Without History (Shallow Mode)

For importing external repos where we don't want to join histories:

- Each sync from monorepo appears as single commit in child
- Child repo stays lean (no monorepo history bloat)
- Shallow can upgrade to full (just start including history)
- Full cannot downgrade to shallow (would require rewriting history)

Mode is recorded in trailers per `r[GZ001.goals.metadata-in-git]`.

### `git zoom clone <url>` (née `zoom fetch`)

Imports an external repository into the current path as if we just zoomed out of it:

```bash
cd src/bin
git zoom clone https://github.com/jeremyBanks/bin
# Creates branch: trunk,path=src/bin
# Sets up appropriate trailers so this path is now "zoom-related" to that repo
# Error if src/bin already has content (use zoom in for existing paths)
```

This is like `git clone` but instead of creating a new worktree, it grafts the repo into the current tree at the current path, establishing the zoom relationship. The external repo's HEAD becomes the zoomed view; we synthesize the zoomed-out commits with appropriate trailers.

## GZ001.verification.manual

Some requirements need manual verification or are verified by implication from other rules.

The no-history-edit constraint is verified by ensuring all zoom operations only create new commits (merges, synthetic commits) and never use `git rebase`, `git commit --amend`, `git filter-branch`, or force-push.
v[GZ001.constraints.no-history-edit]
