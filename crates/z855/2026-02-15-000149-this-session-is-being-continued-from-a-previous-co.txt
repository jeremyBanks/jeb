⏺ The key insight is that these are different input patterns:

  1. Case with 8|ABCDEFGH: Input contains the 8-byte string "ABCDEFGH" embedded
  in zeros
  2. Case with ~ABCDEFGnb@R&: Input contains the 7-byte string "ABCDEFG"
  embedded in zeros

  There is no "H" in the second input - the pattern generator creates separate
  chunks for each length from A through Z.

  The ~ escape is specifically for exactly 7 bytes of safe characters. When
  "ABCDEFG" appears at a non-aligned position (like position 4), the canonical
  encoder:

  1. Encodes the prefix bytes (bytes 0-3) as extended base-85 digits: 0000
  2. Adds the escape marker: ~
  3. Adds the 7 raw safe bytes: ABCDEFG
  4. Encodes the partial trailing block to maintain length invariant: nb@R&

  The nb@R& represents the encoded form of the bytes immediately after "ABCDEFG"
   (bytes 11-14), using the canonical minimum representation that accounts for
  what came before.

  This is working as designed - there's nothing to fix. The encoder correctly:
  - Uses 8| for 8-byte safe runs
  - Uses ~ for 7-byte safe runs
  - Uses _ for 6-byte safe runs
  - Uses ; for 5-byte safe runs

  Each pattern in your comparison file tests a different length of the alphabet
  moving through a 64-byte zero-filled block. The encoder is showing you exactly
   how it handles each distinct input case canonically.
